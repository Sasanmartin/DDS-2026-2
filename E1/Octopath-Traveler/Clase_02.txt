Names

“Selecting names for variables, methods, and other entities is one of the most
underrated aspects of software design. Good names are a form of documentation: they
make code easier to understand. They reduce the need for other documentation and
make it easier to detect errors. Conversely, poor name choices increase the complexity
of code and create ambiguities and misunderstandings that can result in bugs. Name
choice is an example of the principle that complexity is incremental. Choosing a
mediocre name for a particular variable, as opposed to the best possible name,
probably won’t have much impact on the overall complexity of a system. However,
software systems have thousands of variables; choosing good names for all of these will
have a significant impact on complexity and manageability.”
– John Ousterhout

Descuentos más comunes:
Nombres poco descriptivos.
Métodos con nombres muy similares que hacen cosas distintas.
Nombres de métodos que no son verbos o frases verbales (acciones).
Nombres de clases/variables que no son sustantivos.
No encapsular constantes (i.e., tener números o strings sueltos en el código).
Ser inconsistente en cómo se nombran las cosas:
Usar distintos nombres para el mismo concepto (e.j., get, fetch, retrieve).
Escribir cosas similares de forma distinta (e.j., atributos publicos con y sin )
